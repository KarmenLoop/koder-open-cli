# Put the authorization service into operation

The source repository is private: `KarmenLoop/koder-open-cli-source`. The empty dedicated acceptance repository is private: `KarmenLoop/koder-open-cli-receipts`. Neither existence nor a passing fixture means customer activation is live. The current distributed candidate keeps activation closed until the following configuration exists.

1. In the publisher's GitHub account, open **Settings → Developer settings → OAuth Apps → New OAuth App**. Name it **Koder Open CLI**, set the homepage to `https://karmenloop.com`, and use a company-controlled callback URL. Enable **Device Flow**. Copy only the public Client ID into the client settings. No client secret is embedded in the device-flow client. Each customer approves their own device login; the publisher's existing GitHub CLI session cannot substitute for that approval.
2. Provision a company-controlled HTTPS origin for the issuer. Deploy this repository on a Linux server with Node 22 or later. Install the example systemd unit after replacing paths and creating the unprivileged `koder-issuer` account. The server binds to `127.0.0.1:8381`; place it behind the company's HTTPS reverse proxy. Limit POST bodies to 16 KiB, enforce request timeouts and rate limits, and avoid access logging credentials or request bodies.
3. Generate an Ed25519 signing key on the server or in its key manager. Keep the private key readable only by the service. Grant the service a fine-grained GitHub credential restricted to **Contents: read/write** for the dedicated receipt repository. Store it in the deployment secret manager, never in a release or build input. The example environment file lists names only.
4. Run `node service/preflight.mjs` in that deployment environment. It checks the key and actual repository privacy without writing a customer receipt. A successful result prints the public signing key. The current unconfigured local environment correctly fails with the missing setting names.
5. Create a separate JSON file containing only `clientId`, `serviceUrl` (an HTTPS origin), and `publicKey` (Ed25519 PEM). Run `node scripts/configure-activation.mjs public-settings.json`, inspect `resources/activation.json`, and rebuild both native clients. This tool refuses unexpected fields, private keys and incompatible endpoints. Never replace the client's verification gate with a local flag.
6. With the resulting binary, read `koder-open legal list`, explicitly accept the displayed bundle, and run `koder-open auth login --accept-terms <displayed-digest>`. Complete the GitHub device page as the intended test customer. Confirm the private terms archive and minimal receipt exist before accepting the signed authorization result. Check renewal, sign-out, changed terms and account revocation using a dedicated test account and installation.
7. Configure the selected model using the actual account's model ID and the name of a credential environment variable. Start CLI, TUI or Studio from that environment. Run a synthetic task, verify a passing answer and a failing output check, then import an approved practice skill and repeat. Real model adapter evidence is separate from this full signed-activation acceptance.

Record the HTTPS origin, OAuth App owner, public Client ID, signing public-key fingerprint, deployment revision, private receipt commit and both native binary hashes in a private release receipt. Do not attach customer tokens, private keys, skill text or task content. Choose and publish the real hosting, retention and privacy details before collecting customer records. The current service templates have not been deployed to a company host.
